# Safety-Aware Operations Dashboard for an On-Premises Integration Platform

## Система

Це on-premises платформа інтеграції даних, розгорнута всередині закритої інфраструктури. Вона отримує інформацію з кількох внутрішніх і зовнішніх систем, синхронізує її з локальним сховищем, приводить до спільної моделі та формує прикладні проєкції для інших сервісів.

Типовий потік обробки:

```text
Джерела
   ↓
Отримання та первинна валідація
   ↓
Синхронізація з локальним сховищем
   ↓
Нормалізація та зіставлення
   ↓
Побудова прикладних проєкцій
   ↓
Калібрація та контроль узгодженості
   ↓
Дані для внутрішніх сервісів
```

Джерела мають різні структури, ідентифікатори, правила оновлення та рівень якості. Тому синхронізація не зводиться до копіювання записів. Платформа визначає відповідність сутностей, відновлює зв’язки, нормалізує значення, усуває дублікати, вирішує конфлікти та застосовує правила пріоритету.

Калібрація — це додатковий етап після первинної синхронізації. Він перевіряє узгодженість даних, уточнює зіставлення та готує результат до використання прикладними сервісами.

## Бізнесова цінність

Платформа зменшує ручне перенесення й звіряння даних між системами та створює одну контрольовану операційну картину. Dashboard скорочує час діагностики, робить зміни пояснюваними й знижує ризик пропустити завислий або частково успішний процес. Цінність обраного vertical slice — не косметична: оператор швидше переходить до правильного періоду, не працює зі старим UI-станом і водночас не втрачає критичний alert через часовий фільтр.

## Чому це не просто Azure Data Factory

ADF або інший ETL-інструмент може переміщати дані, виконувати типові трансформації, запускати pipeline за розкладом і повторювати технічно невдалі операції. У цій системі transport та orchestration є лише одним рівнем.

Основна складність знаходиться у прикладній логіці:

- визначення ідентичності сутностей між джерелами;
- об’єднання та пріоритизація суперечливих значень;
- побудова цільової моделі, якої немає в жодному окремому джерелі;
- підтримка прикладних інваріантів;
- ідемпотентне повторне виконання;
- контроль конкурентних запусків і часткових результатів;
- аудит змін на рівні сутностей та полів;
- зв’язування запуску, помилки й результату;
- пояснення стану системи оператору.

ADF міг би виконувати частину transport або orchestration, але не замінив би прикладну модель, калібрацію, контроль інваріантів та операційну observability платформи.

On-premises розгортання також є свідомим обмеженням: частина джерел доступна лише у внутрішній мережі, а дані, журнали й облікові контексти не повинні залишати контрольоване середовище.

## Операційна проблема

Платформа виконує багато фонових процесів. Вони можуть завершитися успішно, частково, з помилкою або залишитися активними довше очікуваного. Технічно успішний процес також може сформувати неправильну або неповну проєкцію.

Для супроводу використовується operations dashboard, який показує:

- історію запусків та їхні статуси;
- тривалість виконання;
- помилки й довготривалі активні процеси;
- кількість створених або змінених сутностей;
- зміни окремих полів у форматі `old → new`;
- агреговану активність за вибраний період;
- записи, що потребують уваги оператора.

Dashboard об’єднує дані з різною часовою семантикою. Завершені запуски та зміни можна відбирати за вибраним періодом. Але довготривалий активний процес не можна приховувати лише тому, що він почався раніше. Це safety invariant: актуальна операційна проблема має залишатися видимою незалежно від звичайного date range.

Ручна зміна діапазону створювала неконсистентний стан UI:

- поля вже містили нові дати;
- таблиці ще показували попередній період;
- quick-фільтр залишався активним;
- пагінація та вибраний запис могли не відповідати новому запиту.

Audit-записи також були складними для інтерпретації: технічні ключі та назви полів не пояснювали зміну без знання внутрішньої моделі.

## Реалізоване рішення

Після заповнення повного ручного діапазону dashboard тепер:

- автоматично завантажує актуальні дані;
- не виконує запит із неповним діапазоном;
- повертає пагінацію на першу сторінку;
- очищує поточний selection;
- деактивує несумісний quick-фільтр;
- зберігає видимість критичних активних alerts поза звичайним часовим фільтром.

Для аналізу змін додано:

- структуроване представлення складених ключів;
- metadata-описи сутностей і полів;
- окреме відображення попереднього та нового значення;
- контекст, достатній для аналізу без читання source code або raw JSON.

Зміна покращує не окрему кнопку, а консистентність переходу dashboard між станами та якість операційної діагностики.

## Інженерний підхід

Робота виконувалась як контрольована brownfield-зміна:

1. Read-only аналіз UI, backend-запитів і тестів.
2. Відновлення фактичної поведінки системи.
3. Відокремлення UI-дефекту від safety invariant.
4. Формалізація функціональних вимог і acceptance scenarios.
5. Обмеження blast radius dashboard-сегментом.
6. Реалізація та цільові regression tests.
7. Повна non-live перевірка solution.
8. Перевірка diff і складу commit.

Агент виконував пошук, аналіз залежностей, реалізацію та перевірки. Людина визначала правильну семантику, межі зміни, достатність доказів, готовність до commit і допустимий рівень публічності.

## Результат

- `1,285` тестів пройшли.
- `10` live integration tests явно виключено з прогону.
- `0` тестів упало.
- Authentication, transport і логіка фонових процесів не змінювалися.
- Сторонні робочі файли не потрапили до commit.
- Публічний evidence package не містить приватного коду або реальних операційних даних.

## Обмеження

- UI regression test перевіряє згенеровану поведінку шаблону, а не повний browser E2E flow.
- Live integration tests не входили до зафіксованого regression run.
- Синтетичні mockups демонструють UX і семантику станів, але не доводять pixel-level відповідність приватному застосунку.
- Публічний reviewer може перевірити вимоги, процес, traceability та evidence package, але не приватний diff.
- Повна перевірка конфіденційності відео залишається ручною.

## Коротко

Це модернізація operations dashboard для on-premises integration platform із власною прикладною моделлю. Платформа синхронізує дані з кількох систем, нормалізує їх, будує проєкції та виконує додаткову калібрацію. Реалізована зміна забезпечує консистентну часову навігацію, зберігає видимість критичних процесів і робить audit-зміни зрозумілими без доступу до сирих логів або внутрішнього коду.
